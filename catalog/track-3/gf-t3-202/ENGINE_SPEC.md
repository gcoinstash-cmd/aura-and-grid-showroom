Mathematical Foundation & Fixed-Point Microunit Arithmetic ### 2.1 The Floating-Point Drift Problem Traditional financial systems utilizing IEEE 754 floating-point numbers (`float32`, `float64`) suffer from binary representation errors (e.g., $0.1 + 0.2 \neq 0.3$), cumulative rounding drift, and non-deterministic behavior across disparate CPU architectures. In high-frequency matching engines, rounding drift causes phantom cash balances and broken clearing reconciliation. ### 2.2 Integer Microunit Representation APEX-202 standardizes on fixed-point integer microunits with a scale factor of $\lambda = 1,000,000$ ($10^6$ units per standard decimal base): $$\text{Price}_{\text{micros}} = \text{round}(\text{Price}_{\text{decimal}} \times 10^6)$$ $$\text{Quantity}_{\text{micros}} = \text{round}(\text{Quantity}_{\text{decimal}} \times 10^6)$$ - **Tick Size**: Enforced in integer steps (e.g., $10,000\text{ micros} = 0.01\text{ pts}$). - **Lot Size**: Enforced in integer steps (e.g., $1,000\text{ micros} = 0.001\text{ units}$). - **Settlement Amount**: Quotation settlement is computed deterministically: $$\text{Settlement}_{\text{micros}} = \left\lfloor \frac{\text{FillPrice}_{\text{micros}} \times \text{FillQuantity}_{\text{micros}}}{10^6} \right\rfloor$$ Using integer floor division `//`, this equation yields identical, bit-for-bit results across all operating systems and architectures. --- ## 3. Data Structures & Algorithmic Complexity Proofs ### 3.1 Memory Topology The APEX-202 Order Book employs a hybrid dual-layer data structure: ``` ┌────────────────────────────────────────┐ │ OrderBook Engine │ └──────────────────┬─────────────────────┘ │ ┌─────────────────────────┴─────────────────────────┐ ▼ ▼ ┌───────────────────────┐ ┌───────────────────────┐ │ Bids Subsystem │ │ Asks Subsystem │ │ (Max-Heap by Price) │ │ (Min-Heap by Price) │ └──────────┬────────────┘ └──────────┬────────────┘ │ │ ▼ ▼ ┌───────────────────────┐ ┌───────────────────────┐ │ PriceLevel Map (Dict)│ │ PriceLevel Map (Dict)│ │ price -> FIFO Queue │ │ price -> FIFO Queue │ └──────────┬────────────┘ └──────────┬────────────┘ │ │ ▼ ▼ ┌───────────────────────┐ ┌───────────────────────┐ │ Order Node [FIFO] │ │ Order Node [FIFO] │ │ (id, price, qty, time)│ │ (id, price, qty, time)│ └───────────────────────┘ └───────────────────────┘ ``` ### 3.2 Complexity Proofs Let $N$ denote the total number of open orders in the book, and $P$ denote the number of unique price levels ($P \le N$). #### Proof 1: Best-Bid and Best-Ask Access in $O(1)$ - **Mechanism**: The top of the price heap stores the current highest bid (inverted max-heap root) and lowest ask (min-heap root). - **Complexity**: Peeking at the root of a binary heap is an index lookup at index `0`. - **Amortized Bound**: With lazy pruning of zero-volume exhausted price levels, `peek_best_bid()` and `peek_best_ask()` operate in strictly $O(1)$ amortized time. #### Proof 2: Order Insertion in $O(\log P)$ - **Case A (Price Level Exists)**: Hash map lookup `price_levels[price]` is $O(1)$. Appending the order to the end of the FIFO queue is $O(1)$. Updating level volume is $O(1)$. Indexing `orders_by_id[order_id]` is $O(1)$. Total: $O(1)$. - **Case B (New Price Level Created)**: Inserting the new price into the binary heap via `heapq.heappush` is $O(\log P)$. Allocating the queue is $O(1)$. Total: $O(\log P)$. - **Overall Insertion**: $O(\log P) \le O(\log N)$. #### Proof 3: Order Cancellation in $O(1)$ Amortized / $O(\log P)$ Worst - **Mechanism**: Order pointer is fetched from `orders_by_id` in $O(1)$. The order is marked cancelled or removed from the FIFO deque. The price level volume is decremented in $O(1)$. - **Level Depletion**: When price level volume reaches 0, it is removed from the active hash map in $O(1)$ and pruned lazily from the heap root during the next best-price access. #### Proof 4: Matching Execution in $O(M)$ where $M$ is Number of Fills - Incoming aggressive taker order sweeps resting maker orders from top-of-book in strict FIFO order. - Each match consumes either the full maker order, full taker order, or both. - For $M$ generated fills, time complexity is strictly $O(M \log P)$. --- ## 4. State Machine & Execution Semantics ### 4.1 Order Lifecycle State Transition ``` [SUBMITTED] │ ├─── (Crossing Spread) ───► [PARTIALLY_FILLED] ───► [FILLED] │ │ │ └─── (Cancel) ───► [CANCELLED] │ ├─── (Resting on Book) ───► [OPEN / RESTING] │ │ │ └─── (Cancel) ───► [CANCELLED] │ └─── (Invalid / Rejection) ──► [REJECTED] ``` ### 4.2 Matching Invariants 1. **Spread Invariant**: Under continuous trading, Best Bid Price must always be strictly less than Best Ask Price ($\text{BestBid} < \text{BestAsk}$). If $\text{BestBid} \ge \text{BestAsk}$, an immediate matching event is triggered until the inequality holds. 2. **Price Priority**: An aggressive buy order must match against the lowest available ask price first. An aggressive sell order must match against the highest available bid price first. 3. **Time Priority (FIFO)**: At the same price level, orders must be matched in the exact chronological sequence of their arrival timestamp ($T_1 < T_2 \implies \text{Order}_1 \text{ matches before } \text{Order}_2$). 4. **Volume Conservation**: For every fill, $\Delta \text{MakerQuantity} = \Delta \text{TakerQuantity} = \text{FillQuantity}$. Total executed quantity equals total traded quantity. 5. **Non-Negative Inventory**: Residual quantities on resting orders must be strictly $> 0$. An order whose remaining quantity reaches 0 is immediately purged from the active book. --- ## 5. Audit & State Snapshotting Protocol 1. **Monotonic Audit Sequencing**: Every state modification (order placed, cancelled, partially filled, filled) increments a strictly monotonic sequence counter: $$S_{t+1} = S_t + 1$$ 2. **Hash Chained Trade Records**: Each trade settlement event incorporates the cryptographic SHA-256 hash of the prior trade: $$H_i = \text{SHA256}(H_{i-1} \parallel \text{Seq}_i \parallel \text{Price}_i \parallel \text{Qty}_i \parallel \text{Maker}_i \parallel \text{Taker}_i)$$ This provides tamper-evident audit logs suitable for institutional clearing houses. 3. **Deterministic Snapshot Serialization**: State snapshots produce an exact JSON record of all resting orders, active price heaps, and sequence indices. Restoring from a snapshot guarantees byte-for-byte identical internal state.
